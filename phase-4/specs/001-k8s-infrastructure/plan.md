## Summary

This plan outlines the implementation of the Local Kubernetes Infrastructure (Phase IV) to evolve the Todo App from a Docker Compose setup to a scalable Kubernetes architecture on Minikube. The implementation will involve containerizing both frontend (Next.js) and backend (FastAPI) applications using optimized Dockerfiles generated by Docker AI (Gordon), creating a comprehensive Helm chart for deployment, and ensuring proper service communication, configuration management, and observability. The approach follows cloud-native principles with in-cluster Postgres database, stateless application pods, and AI-assisted infrastructure management.

## Technical Context

**Language/Version**: JavaScript/TypeScript (Node.js 18+) for frontend, Python 3.11+ for backend
**Primary Dependencies**: Next.js 16+, FastAPI 0.104+, PostgreSQL 15+, Docker, Helm 3+, Kubernetes 1.28+
**Storage**: PostgreSQL database (in-cluster Postgres pod for stateful storage)
**Testing**: pytest for backend, Jest/React Testing Library for frontend
**Target Platform**: Kubernetes (Minikube) for container orchestration
**Project Type**: Web application (frontend + backend + database)
**Performance Goals**: Support 100 concurrent users, <200ms p95 response time for API requests
**Constraints**: All infrastructure must be defined via Helm Charts, no manual YAML for K8s manifests
**Scale/Scope**: Single tenant Todo App supporting up to 1000 users with persistent data storage

### Cloud-Native & AIOps Compliance Gates:
- [ ] Container-First: All services must be containerized using Docker (use Docker AI for optimization)
- [ ] Kubernetes Orchestration: All deployments must use Kubernetes (Minikube) as the orchestration platform
- [ ] Infrastructure as Code: All infrastructure must be defined via Helm Charts (no manual kubectl commands)
- [ ] AIOps Workflow: Docker AI (Gordon), kubectl-ai, and Kagent must be used for respective tasks
- [ ] Statelessness: Application pods must be stateless with externalized state (PostgreSQL)
- [ ] Configuration Management: Environment variables must be mapped via K8s ConfigMaps/Secrets
- [ ] Observability: All pods must have liveness/readiness probes configured
- [ ] Zero Manual YAML: No manual Kubernetes manifest writing (AI-generated only)

### Source Code (repository root)

The existing project structure will be extended with Kubernetes deployment artifacts:

```text
backend/
├── src/
│   ├── models/
│   ├── services/
│   └── api/
├── Dockerfile                    # Generated by Docker AI (Gordon)
└── tests/

frontend/
├── src/
│   ├── components/
│   ├── pages/
│   └── services/
├── Dockerfile                    # Generated by Docker AI (Gordon)
└── tests/

k8s/
└── helm/
    └── todo-app/                 # Helm chart for the entire application
        ├── Chart.yaml
        ├── values.yaml
        ├── templates/
        │   ├── backend-deployment.yaml
        │   ├── backend-service.yaml
        │   ├── frontend-deployment.yaml
        │   ├── frontend-service.yaml
        │   ├── postgres-statefulset.yaml
        │   ├── postgres-service.yaml
        │   ├── secrets.yaml
        │   ├── configmaps.yaml
        │   └── networkpolicy.yaml
        └── charts/
            ├── backend/
            ├── frontend/
            └── postgres/
```

**Structure Decision**: Web application structure with separate frontend and backend services plus a dedicated Helm chart for Kubernetes deployment. The existing backend and frontend directories will be extended with Dockerfiles, while a new k8s/helm directory will contain all Kubernetes deployment artifacts organized as a Helm chart.
